# Contributing

Thanks for looking. ACP Devtools is an npm-workspaces monorepo: TypeScript
(strict, NodeNext), Node ≥ 22, Vitest, ESLint + Prettier.

## Build from source

```bash
git clone https://github.com/maksugr/acp-devtools.git
cd acp-devtools
npm install                     # also installs the pre-commit hook
npm run build:full              # builds core, cli, ui, embeds UI in cli dist
cd packages/cli && npm link     # exposes `acp-devtools` globally via symlink
which acp-devtools              # varies by your Node install location
```

Requires Node 22+. CI runs this exact sequence on macOS, Linux, and Windows
(Node 22 and 24), so all three are fair game for development.

## Everyday commands

```bash
npm test               # vitest run — full suite across core / cli / ui
npm run lint           # eslint
npm run typecheck      # tsc --noEmit on core + cli + ui
npm run format         # prettier --write . (CI fails on unformatted files)
npm run precommit      # lint + format check + typecheck + test (also the git hook)
```

## Try it on fixtures

The repo ships seven demo sessions, each stressing a
different surface — a 1392-message marathon, a spec-violating session, a
streaming-heavy one, and so on. Seed them into your capture database and they
show up in the inspector's session picker:

```bash
npm run fixtures:seed          # generate + import all seven into captures.db
acp-devtools ui                # open the inspector and pick one
```

To keep demo data out of your real capture store, point both commands at a
throwaway home — the seeder and the inspector must agree on it:

```bash
ACP_DEVTOOLS_HOME=/tmp/acp-demo npm run fixtures:seed
ACP_DEVTOOLS_HOME=/tmp/acp-demo acp-devtools ui
```

Generate just one instead:

```bash
node fixtures/generate-fat-session.mjs --out /tmp/fat.json
acp-devtools import /tmp/fat.json
```

## UI hot-reload during development

`npm run dev:ui` runs Vite with HMR on port 5173 and serves your capture
database through the same session picker, so component edits hot-reload while
you inspect a real (or seeded) session.

```bash
npm run dev:ui                 # → http://127.0.0.1:5173/  — pick a session
```

## Adding a new agent shortcut

1. Open `packages/core/src/agents/registry.ts`.
2. Add an entry:

    ```ts
    'your-shortname': {
        shortName: 'your-shortname',
        displayName: 'Your Agent',
        description: 'One-line description that shows up in `--agent` help',
        command: 'npx',                       // or a binary name on PATH
        args: ['-y', '@your-scope/your-acp'], // or ['acp']
        // requiresExternalInstall: true,      // if it's a binary, not an npm pkg
        // aliases: [['npx', '-y', 'old-name']], // for deprecated names
    },
    ```

3. Run `npm test`. The inspector turns an agent command into your `displayName`
   in the session picker; cover that in
   `packages/ui/src/lib/captureLabel.test.ts`:

    ```ts
    expect(shortAgentName('npx -y @your-scope/your-acp')).toBe('Your Agent');
    ```

4. Update the _Supported agents_ table in the root `README.md`.
5. Open a PR.

```bash
node fixtures/generate-fat-session.mjs --out /tmp/fat.json
acp-devtools import /tmp/fat.json
acp-devtools ui                        # pick the imported session
```

## Packaging

The CLI is bundled with **tsup**. `@acp-devtools/core` and `@acp-devtools/ui`
are private workspace packages that never reach npm — `core` is inlined into the
CLI bundle, `ui` is embedded as a static bundle at `dist/ui/`. The published
`acp-devtools` tarball is exactly `dist/index.js` plus `dist/ui/`. Runtime deps
pulled from npm are `better-sqlite3`, `ws`, `commander`,
`@agentclientprotocol/sdk`, and `@modelcontextprotocol/sdk`.

## Releasing

Releases are automated: whatever version `main` is at gets published once CI
on that commit is green. So **a PR that ships code carries its own release**:

1. Describe the change under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md)
   ([Keep a Changelog](https://keepachangelog.com/en/1.1.0/) sections).
2. `npm run release:bump -- patch` (or `minor` / `major` / an explicit
   `x.y.z`). It moves the `[Unreleased]` entries under a dated version heading,
   updates the compare links, and rewrites every version literal listed in
   [`scripts/release/version-files.mjs`](scripts/release/version-files.mjs).
3. Update the README and `docs/` if user-visible behaviour changed.

Checks on every PR:

| Check           | Passes when                                                                                                                                                                                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ci-ok`         | lint, typecheck, tests, build and the packed-tarball smoke test pass on Linux / macOS / Windows × Node 22 / 24; the Homebrew formula installs and passes `brew test` on macOS against a tarball packed from the PR |
| `release-check` | all version literals agree; shipped files (anything under `packages/` except tests) changed ⇒ version bumped above `main`, CHANGELOG section written, not yet on npm or tagged                                     |
| `ship-gate`     | a maintainer added the `ship` label; pushing commits that change the diff removes it again (updating the branch from `main` doesn't)                                                                               |

With all three green, GitHub auto-merges the PR (squash). The
[Release workflow](.github/workflows/release.yml) then publishes to npm with
provenance (trusted publishing — no token in the repo), tags `vX.Y.Z`, creates
the GitHub Release from the CHANGELOG section and bumps the Homebrew formula in
[maksugr/homebrew-tap](https://github.com/maksugr/homebrew-tap) — only after
the updated formula installs and passes `brew test` on macOS
([`scripts/homebrew/test-formula.sh`](scripts/homebrew/test-formula.sh)). Each step
skips itself when already done, so re-running a failed release finishes it.

Docs, CI and test-only PRs need no bump and publish nothing. To merge
shipped-file changes without publishing, a maintainer adds `no-release`.

One-time repository setup (merge settings, labels, the `main` ruleset) lives in
[`scripts/setup-github.sh`](scripts/setup-github.sh); the npm trusted-publisher
link and the optional `HOMEBREW_TAP_TOKEN` secret are described at its top.

## Pre-commit hook

`simple-git-hooks` is wired in via the root `prepare` script, so a fresh `npm
install` registers it. The hook runs `npm run precommit`. To skip it on a single
commit (genuine emergencies only): `SKIP_SIMPLE_GIT_HOOKS=1 git commit ...`.

## Conventions

- 4-space indentation everywhere (TS, JSON, configs, Markdown), enforced by
  Prettier + EditorConfig.
- ESM with explicit `.js` import extensions (NodeNext); `import type` for
  type-only imports.
- Tests are colocated `*.test.ts`; ship a test in the same change as the code.
- Comments only for non-obvious _why_ — no narration of what the code does.

## Security design rules

These are **constraints**, not guidelines — apply before touching anything
that exports session data or returns frame contents to a consumer. User-
facing context is in the README's
[Security & privacy](README.md#security--privacy) section; the rules
themselves live here so they're the first thing a contributor sees:

1. **`acp-devtools export --raw` is the only path that produces an
   un-redacted JSON export.** Don't add a `raw` toggle to the UI, MCP, or any
   future share channel. UI's `downloadExport.ts` and the MCP tool handlers
   carry `SECURITY:` comments at the redaction call sites — keep them.
2. **MCP redaction has no opt-out.** Every tool that returns frame contents
   or a view derived from them (currently `get_message`,
   `get_session_messages`, `search_messages`, `get_session_metadata`,
   `get_session_summary`, `diff_sessions`) routes through
   `redactedReadMessages` or post-processes its output via `redactMessage`.
   Adding a new MCP tool that returns frames? Same rule.
3. **`search_messages` matches the pre-redaction bytes but returns the
   redacted copy** — without this, an LLM asked to find by a token fragment
   would quote the live token back to the user.

The single source of truth for what counts as "sensitive" lives in
`packages/core/src/storage/redact.ts` (`SENSITIVE_HEADER_NAMES`, the
`proxyConfig` subtree rule, and `CREDENTIAL_LIST_KEYS` for the spec's
`{ name, value }` header / env lists). When you discover a new auth-bearing field
that should be masked, add it there once and every channel inherits.
